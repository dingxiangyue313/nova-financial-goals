# NOVA 全量接线缺口审计与阶段开发计划

审计日期：2026-09-28

## 一、结论

当前系统已经具备一条真实主链路：

`输入目标 → Agent 解析/规划 → 可行性展示 → Approval Snapshot → 用户确认 → Banking Tool 写操作 → Financial Twin 更新 → Activity 审计`

这条链路不是纯 Demo。但整个产品还没有达到“页面上每个入口都由真实状态和真实服务支撑”的标准。当前主要问题是：核心链路已经服务端化，外围功能仍混有静态文案、固定目标 ID、无事件按钮和概念型安全卡片。

## 二、按钮与功能接线盘点

### A. 已形成真实闭环

| 页面/入口 | 当前逻辑 | 状态 |
| --- | --- | --- |
| 创建目标 → 下一步 | 调用 `/api/agent`，生成结构化意图和工具计划 | 已接线 |
| 调整额外消费金额 | 调用 Financial Twin `simulate_expense` | 已接线 |
| 选择保守/平衡/加速方案 | 写入服务端 Twin 状态 | 已接线 |
| 生成审批快照 | 调用 `create_approval_snapshot`，冻结参数并返回 Hash | 已接线 |
| 确认创建/修改目标 | `confirm_approval` 后执行 `create_goal` / `update_goal` | 已接线 |
| 激活目标方案 | 审批后调用 `activate_goal`，校验 Twin Version | 已接线 |
| Activity 页面 | 调用 `get_activity` 获取服务端审计 | 已接线 |
| Financial Twin 刷新 | 读取统一服务端 Twin | 已接线 |
| 金额篡改攻击 | 真实审批一个金额、篡改后请求服务端，预期被拒绝 | 已接线 |
| Tools 列表 | 从 Banking Tools discovery 接口读取 | 已接线，但只读展示 |
| 底部导航、返回、金额隐藏 | 本地 UI 状态切换 | 已接线 |

### B. 有界面但逻辑不完整

| 页面/入口 | 当前问题 | 需要补齐 |
| --- | --- | --- |
| “NOVA 的理解” | 金额、日期和约束仍是固定文案 | 绑定 Agent 结构化实体，显示置信度、Evidence ID 和字段级修改 |
| 创建目标审批参数 | 名称和目标日期存在前端默认值 | 完全采用 Agent 草案；缺字段时进入补充信息状态，禁止偷偷补默认业务值 |
| 调整每月投入 / 调整完成日期 | 两个按钮目前都只跳到同一个页面 | 分别创建不同 Scenario，并显示各自影响和推荐理由 |
| 目标列表 | 列表来自 Twin，但“查看日本旅行”仍固定目标 | 目标卡片携带真实 `goalId`，支持查看、修改、暂停和删除审批 |
| 安全场景标签 | 除金额篡改外由本地 `runSecurityDemo` 生成 | 每个场景都调用真实 Banking Sandbox，并展示 Operation ID / Audit ID |
| Tools 页面 | 只展示工具元数据 | 增加只读工具调试器；写工具只能从审批流程发起 |
| 审计后台 | `hash_prev → hash_n` 是展示文本 | 读取真实审计链、Hash、请求/决策/Receipt 关联关系 |
| Activity | 已有真实数据，但无筛选、分页、详情和导出 | 增加分类筛选、Evidence 详情、Operation 状态查询、证据包导出 |
| Profile | 三行看起来可点击，实际没有交互 | 接入通知偏好、授权管理、Mandate 管理、审计导出 |
| Agent 结果卡 | 只显示 Provider 和工具数量 | 展示计划、Permission、Risk、Tool Receipt、降级原因和 token/延迟 |

### C. 当前无处理逻辑的按钮

- 创建页的“修改设定”。
- 创建页的“补充更多信息”。
- Profile 中的“数据与授权”。
- Profile 中的“审计与导出”。
- Profile 中的 Financial Twin 入口。

这些入口必须在下一阶段处理：要么实现真实交互，要么在未实现前明确禁用并标记“即将开放”，不能保留伪可点击状态。

### D. 后端已有能力但新版前台尚未消费

- 账户、交易、账单查询。
- 转账草案、审批、执行与状态查询。
- Mandate 创建、版本、过期和执行边界。
- 外部 Agent 签名请求与重放防护。
- 购物逐笔确认、餐饮安全余额阻断、人工复核。
- Permission Check、Risk Check。
- MCP 对外调用协议。
- Goal Flow 独立状态机接口。
- 健康检查和运行状态。

## 三、为什么之前会出现“有时有密钥、有时没有”

本地页面由 Wrangler 启动时会读取 `frontend/.dev.vars`，但基线评测脚本此前只读取启动终端的环境变量。因此同一台电脑上，页面运行和独立评测是两个环境来源。

本轮已经统一：

- 本地开发继续使用被 Git 忽略的 `frontend/.dev.vars`。
- 自动化基线评测也会自动读取同一文件。
- shell 或部署平台显式提供的变量仍具有更高优先级。
- 生产部署仍必须使用平台 Secret，不能把本地文件提交到仓库。

## 四、推荐的下一轮开发顺序

### 阶段 1：消灭假按钮与硬编码数据（最高优先级）

目标：新版前台所有可点击元素都有明确结果，Goal-first 主线不再依赖固定日本旅行数据。

工作项：

1. 将 Agent 的实体、Evidence、Feasibility 真实绑定到“我的理解”。
2. 实现字段级修改和补充信息表单。
3. 将两种目标影响方案拆成独立 Scenario。
4. 去除固定 `goal_japan_001`、固定金额和默认目标日期。
5. 目标卡支持按真实 `goalId` 查看和修改。
6. 无法在本阶段实现的入口明确禁用，不保留空按钮。

验收标准：

- 页面扫描不存在没有 `onClick` 或提交逻辑的交互按钮。
- 输入不同目标时，理解卡、可行性、审批参数和最终目标均随输入变化。
- 缺少金额或日期时系统主动追问，不生成带猜测值的写操作。

### 阶段 2：把 Banking Tools 接到用户场景

目标：后端已有银行能力不再只停留在工具列表。

工作项：

1. 恢复并重做 Life 页面：交通自动执行、购物等待确认、餐饮超限阻断。
2. 实现购物请求确认与拒绝 UI。
3. 实现转账草案 → Permission → Risk → Approval → Receipt。
4. 实现“状态未知”后的原 Operation ID 查询。
5. 增加 Mandate 查看、创建、撤销、版本和剩余额度页面。

验收标准：

- 每种 Life 场景产生真实 Tool Receipt 和 Activity 记录。
- 写操作不能从浏览器直接绕过服务端 Permission/Risk。
- 超时请求不重试执行，只能查询原 Operation ID。

### 阶段 3：真实安全控制台与可验证审计

目标：把安全卡片变成比赛现场可操作的攻击实验室。

工作项：

1. 将重放、过期 Mandate、无效签名、高风险、工具超时全部改成真实请求。
2. 审计详情关联 Request、Decision、Approval、Operation、Receipt 和 Twin Version。
3. 实现分类筛选、分页、证据详情和 JSON/CSV 导出。
4. 真实显示 Approval Snapshot Hash 和审计链 Hash。

验收标准：

- 七类安全场景均由服务端返回判定，前端不预先决定结果。
- 任一操作可用 Operation ID 追溯到完整证据链。
- 导出的证据包能够独立说明“谁、何时、基于什么授权、执行了什么”。

### 阶段 4：四页面统一状态与端到端回归

目标：Today、Life、Twin、Activity 不再各自维护解释口径。

工作项：

1. 建立统一客户端数据层和版本失效策略。
2. 所有写操作成功后按 Twin Version 刷新四页面。
3. 增加 Playwright 浏览器 E2E，而不仅是接口级投影测试。
4. 覆盖 360、768、1440 px 和弱网、刷新、重复点击。

验收标准：

- 一次真实操作在四个页面显示相同金额、状态和 Twin Version。
- 浏览器 E2E 覆盖主链路、拒绝链路和恢复链路。
- 不存在刷新页面后状态回退为前端假数据的情况。

### 阶段 5：生产部署与运营保障

目标：从比赛可演示提升为可受控试运行。

工作项：

1. 在部署平台配置 DeepSeek、外部 Agent 签名和数据库 Secret。
2. 将单实例限流升级为 D1/KV/Durable Object 分布式限流。
3. 接入结构化日志、指标、追踪、SLO 和告警渠道。
4. 完成日志脱敏测试、Secret 轮换和泄漏处置预案。
5. 完成正式域名、跨设备、故障注入和回滚演练。

验收标准：

- Secret 不进入源码、构建产物、日志和前端响应。
- 多实例下限流和幂等仍然成立。
- Provider、数据库、工具错误能在规定时间内触发告警。

## 五、下一步建议

下一步直接开始“阶段 1：消灭假按钮与硬编码数据”。这是当前投入产出比最高的一步，因为它决定评委点击任何入口时，产品是否仍像一个完整系统，而不是只在规定演示路径上成立。
