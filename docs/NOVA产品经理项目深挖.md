# NOVA 产品经理项目深挖｜事实、决策与面试素材

> 本文供产品经理求职使用，重点解释个人做出的产品判断和可核对的交付，不是简历成稿。整理依据为本仓库截至 2026-10-28 的产品、设计、用户流程、实现记录，以及用户先前提供的竞品矩阵与对话截图。当前工作分支仍有未提交改动，测试数字和完成范围应以最终发布记录更新。

## 1. 一句话讲清项目

NOVA 是一款使用**模拟金融数据**的目标驱动 AI 财务副驾驶原型。它帮助不愿持续记账的用户判断旅行、学费等生活目标能否按期实现；当财务情况变化时，解释对目标的影响、提供少量可比较的调整方案，并在用户确认后完成受控的模拟金融操作。

项目不是已上线的银行产品，不连接真实账户，也不转移真实资金。求职叙述应突出**产品发现、范围取舍、复杂流程设计和原型交付**。

## 2. 个人角色与团队边界

用户明确说明：**设计和前端由本人完成**。`PRODUCT.md` 中的 Design Owner 职责还包括产品定位、范围与优先级、用户流程、信息架构、页面清单、文案、原型、React 页面、响应式与视觉验收。`NOVA_TWO_TRACK_DEVELOPMENT_PLAN.md` 把 `src/**`、端到端测试与产品交付文档划为产品体验线。这里可据此梳理本人工作，但最终简历仍须按实际参与程度核对每项“独立负责”的表述。

后端 Financial Core、权限与风险引擎、SQLite 持久化、Banking Tools、MCP 和部分测试属于架构线或团队成果。介绍项目整体能力时可以讲，介绍个人贡献时应说清自己如何**定义需求、设计可见状态、对接契约并验收体验**，不要把全部后端实现归为个人独立开发。

## 3. 项目最值得讲的产品问题

传统财务界面容易回答“花了多少钱”，但难回答用户实际关心的“这笔旅行钱能不能在六月前备好”。NOVA 的难点是把多账户与流水、预算、目标日期、应急金保护、订阅费用和后续操作，组织成普通用户能理解的**一个连续任务**。

进一步的矛盾有三组：

1. **低负担与可信数据**：用户不想持续记账，但系统不能用不完整流水假装知道当前余额。
2. **主动服务与提醒噪音**：AI 应发现问题，但不能把每笔波动都变成警报。
3. **行动效率与资金控制**：Agent 可以准备操作，但用户需要看清准确参数、授权范围与执行结果。

这三组矛盾贯穿用户研究、竞品分析、PRD、交互和验收，是面试叙述的主轴。

## 4. 研究如何影响产品决策

### 4.1 用户访谈：把方向性反馈转成约束

`PRODUCT.md` 记录约两位受访者，且部分提问带选项或解释。它支持的是 MVP 方向，而非可推广的市场结论：

| 观察 | 产品处理 |
| --- | --- |
| 不愿每天维护账本或切换多个 App | 优先设计低维护的数据连接与导入路径。 |
| 旅行、学费、开店等具体目标比日常小额消费更值得规划 | 将目标可行性放在首页和第一条体验。 |
| 希望有主动提醒，但不希望频繁打扰 | 普通变化进入安静摘要；显著影响目标时才即时提醒。 |
| 对自动执行的态度存在分歧 | 默认只建议；资金动作逐次确认或受明确授权约束。 |
| 数据连接的便利性依赖来源可信和权限清晰 | 在首次使用和连接流程中解释读取范围、更新时间、撤销与数据不足。 |

**能讲出的判断**：没有把两位用户的偏好直接升级成“用户都愿意让 AI 自动转账”；相反，把分歧转成默认权限设计。这比“做过用户访谈”更能体现产品思考。

**证据限制**：仓库中可找到访谈结论摘要，未找到逐字访谈记录、招募条件或完整研究报告；不要声称完成了大规模定量研究。

### 4.2 竞品矩阵：从能力比较走到优先级

用户提供的研究材料比较 Revolut AIR、SBI NEOBANK ai、DBS digibot、Visa AI/VIC 与工行工小智，覆盖自然语言、财务分析、主动洞察、生成式 UI、工具执行、授权和审计。研究用 **Must-have / Borrow / Differentiate / Don't build** 四类归纳能力，而不是简单统计功能数。

这一过程形成了两层判断：

- 自然语言和基础银行工具是进入赛道的必要能力；它们本身不构成清晰消费者价值。
- 主动洞察、生活目标、动态任务界面和可控执行可以组合成体验机会，但不能把“没有竞品完整组合”未经核实地写成市场唯一性。

最终产品没有停留在最初对话提出的“Morning Financial Brief”主线。`PRODUCT.md` 将首页与第一条体验改为 **Goal Readiness → Plan Activation → Goal Impact**，先回答目标能否实现，再展示主动提醒和执行能力。这个转向是项目最有代表性的定位决策。

**可用面试表达**：竞品研究提供的是候选能力和取舍框架；用户研究把它收敛到目标优先、低噪音、可控授权。两类材料共同决定了首页讲什么、哪些功能先做、哪些能力延后。

## 5. 从 PRD 到可演示产品的两次收敛

### 第一次：从“AI 银行能力”转向“目标能否按时实现”

产品基线把 Consumer Value Track 放在 Competition Capability Track 前面。首页优先展示目标状态、判断依据和下一步；Financial Twin、MCP、Permission Engine 等留作内部能力或必要的信任解释。三条 Hero Experience 排序为：目标可行性与计划、目标影响监测、受授权的模拟操作。目标、数据、方案、确认、凭证形成闭环。

这一步解决了**产品定位**：用户看到的是为生活目标做决定，不需要先理解 Agent 架构。

### 第二次：从三个演示点深化为日本旅行 Money Mission

2026-10-26 的 v0.6 深化 PRD 比较了三个方案：横向覆盖六类银行场景、只强化目标规划、以及用一条目标主线覆盖账单分析、订阅管理、智能转账。最后选择第三种，以日本旅行 ¥8,000、已存 ¥2,000、应急金 ¥20,000 为连续故事。

用户从首页进入后，核对模拟数据和账单证据，看到 CloudBox Plus ¥68 续费如何影响工资前余额，选择保留、提醒或准备取消；再比较稳健、平衡、加速三种资金方案，确认工资到账后次日转入的月度计划，最后进入监测与失败恢复。这个设计用一个目标串起多个官方场景，而非让用户在孤立功能页之间跳转。

**重要版本区别**：2026-10-27 的方案 B 设计包又提出六类场景完整覆盖；截至 2026-10-28，`docs/SIX_SCENARIO_IMPLEMENTATION.md` 记录了六类模拟操作的当前实现，但也明确列出真实用户无引导研究、完整真实模型多轮评测和高级目标能力尚未完成。面试时应分别说明“先做完整 Money Mission 主线”与“随后扩展六类模拟场景”，不要把后期设计包写成早期已验证结果。

## 6. 你负责的设计与前端交付，具体体现在哪里

### 信息架构与视觉

- 保留原版 NOVA 的青绿色、底部导航、手机框和移动端优先结构；首页以目标状态和当前行动为主，而非高密度银行 Dashboard。
- 规划 Home、Goals、Agent、Activity、Profile 的职责：目标判断、目标管理、复杂任务、操作记录、权限和数据管理各有归属。
- `DESIGN_SYSTEM.md` 给出颜色、卡片、排版、按钮、焦点、确认层与手机/桌面适配规则。它要求事实、假设、预测和限制有文字标签，避免用户把推断当成已发生事实。

### 逐屏流程与边界状态

- `USER_FLOW.md` 不只写正常路径，还定义用户输入、系统行为、Agent 行为、确认节点、错误和恢复。关键规则包括：预览与正式执行分离；参数变化使旧确认失效；结果未知先查询原操作，不能重复付款；刷新后恢复服务端任务状态。
- 钱的不同状态被拆开呈现：账单历史不能覆盖当前余额；未来工资、AA 待收、未结算赎回和信用额度不能算作可用现金；创建月度转账计划不等于当场扣款。
- 订阅取消不能把点击确认直接写成“省下 ¥68”；必须看到商户模拟验证后的续费抑制结果。用户界面要解释服务有效期、下次扣费、是否退款和未知结果的处理方式。

### 前端实现

- 仓库现有 `HomeScreen`、`MoneyMissionScreen`、`AgentWorkspaceScreen`、`FinancialServicesScreen` 等页面，以及导入核对、账单摘要、证据抽屉、现金流时间线、三方案对比、操作确认和回执等组件。
- 通过服务端读模型获取金额、日期和阶段；前端负责信息层级与交互，不维护独立的财务计算副本。手机端单列，桌面端为复杂任务提供并排的上下文与对话画布。
- 确认按钮写清具体动作；对加载、空、过期、失败、离线和未知状态提供可理解的下一步。调试与故障注入入口移到单独 `/demo-control`，普通用户页面只保留模拟数据标识。

这些交付能支撑“产品经理能把复杂规则落成可用交互，且亲自完成前端原型”的定位。表述时最好举**一个具体界面决策**，如“余额与账单来源分离”或“未知结果只能查原操作”，比列十几个页面更有说服力。

## 7. 验证过什么，尚未验证什么

| 层次 | 当前可说的事实 | 不能推出的结论 |
| --- | --- | --- |
| 规则与状态 | 2026-10-28 的六场景实施记录写有独立临时数据库服务端回归 387/387、类型检查和构建通过。 | 不能等同真实银行稳定性或最终全平台发布。 |
| 体验验收 | 仓库存在 Money Mission、金融服务、工作台、无障碍等 Playwright 用例，设计要求覆盖 360、768、1440 px。 | 不能在最终浏览器测试结果未归档前宣称全部通过。 |
| 用户研究 | 约两位访谈提供方向性判断。 | 不能称大样本验证、用户增长或付费意愿验证。 |
| 竞品分析 | 五个样本的能力矩阵帮助确定 MVP 取舍。 | 不能称市场唯一性或竞品当前全量功能的已核验事实。 |
| AI 质量 | 系统有确定性回退与真实模型评测入口，部分版本记录真实 DeepSeek 评测。 | 不能用脚本化测试代替开放式多轮任务完成率。 |
| 业务效果 | 原型可以用合成数据跑通模拟任务。 | 没有真实用户转化、留存、资产规模或真实金融操作数据。 |

## 8. 面试最适合深讲的四个案例

### 案例 A：定位转向

**问题**：初期方案把 Proactive、Generative UI、MCP 和银行工具并列呈现，用户难以立即理解价值。  
**判断**：竞品已有自然语言和交易分析，用户访谈又指向具体生活目标。  
**动作**：重排首页与体验优先级，先回答“能否按时实现”，再进入方案、监测、授权。  
**可展示材料**：`docs/NOVA竞品分析.md`、`PRODUCT.md` 的双轨结构、首页优先级和三条 Hero Experience。  
**追问准备**：为什么没有先做 Morning Brief？为什么目标比预算更适合作为主线？

### 案例 B：复杂需求压成一条主故事

**问题**：比赛要求多个核心银行场景，横向堆六个入口会让每条体验都浅。  
**动作**：比较三种方案，选日本旅行 Money Mission 串联账单、订阅、现金流、目标方案和工资事件转账。  
**可展示材料**：v0.6 深化 PRD 第 3、7 节，`USER_FLOW.md`，`DEMO_SCRIPT.md`。  
**追问准备**：为什么选订阅和工资事件？哪些场景被排到后续？后来为什么又扩展六类？

### 案例 C：让 AI 的建议可信

**问题**：财务分析中“可能”“预测”和“已经发生”容易混淆，模型也不能直接批准资金动作。  
**动作**：设计事实/假设/预测/限制标签、逐笔证据下钻、准确确认和独立回执；未知结果只查询原操作。  
**可展示材料**：`DESIGN_SYSTEM.md`、`USER_FLOW.md`、前端 EvidenceDrawer、ActionApproval、ActionReceipt。  
**追问准备**：用户数据不足时显示什么？取消订阅超时时如何避免误导？

### 案例 D：主动但不打扰

**问题**：普通波动若频繁推送，会削弱信任和长期使用。  
**动作**：把主动服务收窄为目标影响监测；常规趋势进入周摘要，显著变化展示目标影响与可调整方案。  
**可展示材料**：`PRODUCT.md` 的产品原则、Goal Impact 需求、`README.md` 的演示流程。  
**追问准备**：显著变化的定义是什么？用户忽略或暂停后系统如何处理？

## 9. 下一轮需要补充的证据

1. **原始访谈材料**：受访者背景、原话、提问方式、编码过程；目前仓库只有总结。
2. **个人贡献记录**：每项设计和前端页面的版本、截图、提交或评审记录；可证明“我亲自做的范围”。
3. **体验验证**：无引导任务测试，记录目标创建完成率、用户能否复述可行性依据、授权理解度、误触与失败恢复情况。
4. **最终发布证据**：同一提交的服务端、浏览器、无障碍、真实模型评测结果与已知限制。
5. **商业判断**：真实需求频次、付费意愿、持续使用，现阶段尚未验证。
