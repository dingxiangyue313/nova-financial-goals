## 1. 产品概述

### 1.1 一句话介绍

NOVA 围绕用户的生活目标，连接账单理解、日期现金流、计划调整和受控金融行动，让用户不仅知道“钱花到哪里”，还知道“目标能否实现、现在该做什么、行动是否真的成功”。

例如，用户希望准备一笔日本旅行资金。NOVA 会把这个目标拆成连续任务：

1. 看懂已有账单和账户信息。
2. 找出影响旅行预算的消费变化和续费。
3. 比较可执行的储蓄节奏与资金安排。
4. 在明确确认后取消不需要的模拟订阅、安排转入或处理同行 AA。
5. 核对旅行报价、支付卡、授权和资金占用。
6. 独立处理机票、住宿、失败订单和退款。
7. 持续区分钱已准备好、订单已付款、服务是否履约和任务是否完成。

产品的核心不是“能回答多少金融问题”，而是让一个有边界、有证据、可恢复的金融任务持续向前推进。

### 1.2 用户痛点

| 用户遇到的问题 | NOVA 的处理方式 |
| --- | --- |
| 钱分散在多个渠道，靠记账难坚持 | 整理导入和模拟连接的数据，保留来源与覆盖范围 |
| 看到月结余，却不知道哪一天会缺钱 | 按日期排列工资、账单、续费和已安排支出，识别资金低谷 |
| 想旅行或培训，但不知道目标是否现实 | 结合目标金额、期限、已准备资金和保护底线试算 |
| 有多个人生目标，同一笔钱容易重复规划 | 在共享现金流中检查多目标投入和占用冲突 |
| 看不懂消费异常或不知不觉被续费 | 将变化、周期扣费和逐笔证据关联起来，允许用户核实 |
| AI 说得合理，却不知道有没有执行成功 | 准备、确认、执行、验证和凭证分开呈现 |
| 支付超时后不敢重试，怕重复扣款 | 保留未知状态和资金占用，优先查询原操作 |
| 旅行订单部分失败，整套计划容易重做 | 保留成功项，只修需要处理的部分 |

### 1.3 目标用户

- 希望为旅行、课程、设备或其他生活目标做准备的年轻用户。
- 拥有多个支付渠道，不愿每天手工记账的用户。
- 对账单、订阅和月内现金流缺乏清晰理解的用户。
- 需要同时协调多个目标，且不能动用应急金的用户。
- 愿意借助 AI 整理信息，但希望保留金融决策和执行控制权的用户。

这些是产品服务对象与设计假设，不代表已经完成市场规模、付费意愿或真实用户留存验证。

### 1.4 产品形态与界面原则

NOVA 是移动端优先的响应式 Web / PWA。界面保留原有青绿色视觉、手机框、底部导航和目标优先的信息层级。

首页首先回答目标和资金准备问题，再提供账单、计划与金融任务入口。技术术语不作为普通用户完成任务的前置知识；签名、权限引擎和状态机主要在底层发挥作用。

模拟故障、样例切换和调试控制集中在独立的 `/demo-control` 中。消费者看到的是业务事件和下一步，不需要先选择想要展示的成功或失败答案。

## 2. 产品组织方式：以 Money Mission 串联六大场景

NOVA 使用 Money Mission 表达持续推进的生活金融任务。一个 Mission 可以跨越账单调查、订阅、转账、理财、卡片和旅行服务，但各个场景仍保留自己的规则与确认边界。

| 场景 | 用户最终要完成的事情 | 核心价值 |
| --- | --- | --- |
| 智能转账 | 核对收款人、转账、处理 AA、安排目标储蓄 | 不混淆对象，不重复扣款，按规则安排资金 |
| 账单分析 | 看懂指定期间的消费、变化与证据 | 从结论下钻到事实，并能修正错误 |
| 理财操作 | 判断适配性、比较产品与现金、申购赎回 | 把风险、费用、用钱时间和结算约束放在一起 |
| 卡片管理 | 申请、审核、限额、支付控制、锁定、挂失与补卡 | 卡片能力与现金、目标资金保持分离 |
| 订阅管理 | 识别可能续费、作决定、取消、提醒与恢复 | 将“发现支出”变成可核对的行动闭环 |
| 跨场景联动 | 接收旅行请求、核对授权、付款、恢复和退款 | 让多步骤任务在失败或变化后仍能继续 |

“覆盖六场景”不等于已经覆盖所有银行业务。每个场景都有明确的模拟范围和不支持的边界。

## 3. 首页与目标管理

### 3.1 首页信息

首页包含：

- 模拟财务日期与数据状态。
- 用户当前目标及准备进度。
- 本月消费、支出变化、近期续费与资金低谷等可复算摘要。
- 查看账单与消费、新建目标、查看计划等入口。
- 数据连接情况与必要的更新说明。

用户可以从一张消费摘要卡进入账单和订阅，而不必先完成演示式步骤向导。数据连接后，已有消费证据不应无故消失。

### 3.2 新建目标与方案比较

用户填写目标名称、金额和用钱日期，在新建目标流程内比较存钱方案，再明确确认选择。

方案包含每月投入、必要时的一次性投入、预计完成日期及限制说明。选择方案本身不会把钱转走，也不会自动创建付款授权。

### 3.3 多目标合同

目标不仅保存一个金额，还可以表达：

- 目标用途、金额、期限与当前月度投入。
- 目标优先级。
- 共同保护底线。
- 最多愿意增加多少月存、允许延期多少天。
- 是否允许此目标进入后续独立付款流程。

合同变更使用版本控制。修改目标不会自动提高旧授权额度；关联计划和旧预览需要按规则重新核对。

### 3.4 多目标共享试算

系统把多个目标放入同一张日期现金流中，防止将同一笔资金重复用于旅行、培训等不同目标。

试算展示最低余额、出现日期、保护底线、各目标剩余缺口和有界调整候选。当前范围限制为最多 20 个目标、366 天预测窗口。

已有实现使用确定性、有边界的搜索与优先级规则，不宣称对所有目标和金融产品求出全局最优解。

## 4. 数据进入、账单整理与 Financial Twin

### 4.1 数据路径

支持模拟渠道数据，以及 CSV、Excel、PDF 和图片账单路径。用户核对识别结果、字段映射和导入问题后，再提交证据批次。

个人文件上传由服务端开关控制；演示可以只使用合成文件。格式支持不意味着能够无误识别任意银行、任意版式的文件。

### 4.2 对账与数据质量

整理流程处理：

- 重复记录与重复批次。
- 内部转账及其对消费统计的排除。
- 原扣款与匹配退款。
- 跨期退款在各自发生期间的影响。
- 分类修正与原始值保留。
- 识别置信度不足和必须核对的问题。
- 批次撤销后的重新计算。

同金额的两笔消费不能直接被当成重复；周期相近的付款也不能直接证明用户实际使用某项服务。

### 4.3 历史证据与权威余额分离

历史账单解释过去发生了什么，账户快照定义当前已核对余额。导入或撤销账单不应凭空改变可支付现金。

例如，导入一份包含历史工资的账单，不等于现在又收到了一笔工资；发现一笔退款记录，也不等于可以忽略其发生日期和配对证据。

### 4.4 Financial Twin 的组成

当前财务状态包括目标、账户快照、归一化交易、导入批次、账单、订阅、日期事件、计划、预留、投资份额、卡片、订单、审批、凭证与审计引用。

它的价值在于让分析与执行读取一致的状态，而不只是由对话模型记住几个金额。

NOVA 尚不将它描述为完整复刻真实个人财务生活的数字孪生：缺失账户、错误分类、不确定未来收入和真实外部数据冲突仍需要明确处理。

## 5. 账单分析功能

### 5.1 多期间账单

用户可选择受支持的月份、年度或年内窗口，查看：

- 总支出、退款及净支出。
- 住房、餐饮、交通、购物、订阅等分类构成。
- 分类金额与交易数量。
- 数据截至日期、覆盖缺口和统计限制。

界面采用分类条形展示和逐笔入口，减少只堆叠数字、难以理解的问题。

### 5.2 动态历史基线

比较窗口根据请求期间和已有连续历史构建，不在所有用户、所有月份上固定使用某三个月。

数据缺失不当作零消费，未结束月份也不等同于最终月度涨幅。缺少可比较历史时，系统展示事实与缺口，而不制造异常结论。

### 5.3 支出变化调查

用户可以查看变化规则、本期与基线期间、金额差异及相关逐笔来源，并标记：

- 这是预期支出。
- 暂时不认识。
- 稍后核对。

反馈附着于相应证据，不删除交易、不自动退款、不据此判定欺诈。证据或分类变化后，旧反馈不能静默沿用到新结论。

### 5.4 分类修正与报告失效

用户发现分类错误时，可从来源详情修正，并重新计算账单。

财务版本变化后，旧期间报告会明确标记失效，提示重新生成。历史更正不覆盖当前权威余额。

## 6. 订阅与代扣管理

### 6.1 周期支出识别

系统从已提供流水中寻找重复商户、相近扣款周期和金额变化，形成“可能是订阅”的线索。

例如 CloudBox Plus 的历史月扣款由 ¥58 变为 ¥68，可以展示扣款日期与来源；但是否仍在使用服务，仍由用户确认。

### 6.2 用户可作的决定

- 保留服务。
- 设置续费前提醒。
- 标记“这不是订阅”。
- 准备取消并进入准确确认。

取消前说明原金额、周期、下次扣款、已付服务期和生效语义。取消未来续费不等于退回已支付费用。

### 6.3 取消闭环与恢复

服务端分别处理成功、拒绝、需商户处理、提交前未受理和提交后未知。

只有验证成功后，预测中才抑制对应未来扣费。未知结果仍保留支出风险，用户应查询原操作，不能把“已提交”当作“已节省”。

停扣后如果出现新扣费，系统关联原交易与取消记录，形成待调查事项，不自动增加退款余额。

### 6.4 本地提醒队列

提醒具备持久记录、稳定编号、到期处理、静默／暂停、稍后提醒、已读和重启去重。

提醒投递在本地收件箱完成，不等于已发送短信、微信或邮件。

### 6.5 最新工作区：逐商户支付卡绑定与换卡

本轮新增了明确的订阅卡绑定、挂失影响和逐商户换卡确认；未知结果需要先查询原换卡操作。

原支付卡未知时不从历史流水猜测。换卡不会自动取消订阅，也不立即扣款。**已通过领域及三尺寸换卡流程验证；绑定只适用于模拟商户。**

## 7. 智能转账与目标储蓄

### 7.1 联系人核对

提供合成联系人列表，使用姓名、备注、尾号和版本区分同名对象。

待核对或版本已变化的联系人不能直接进入新付款或 AA。用户核对尾号后独立确认；该记录仅表示对合成资料的确认，不是银行实名验证。

### 7.2 联系人转账

转账准备与最终执行分开。确认包含对象、来源账户、金额和费用，执行时重新核对联系人版本、可用资金与保护规则。

同一操作重复确认不重复扣款。结果未知时，优先查询原操作，保留必要占用。

### 7.3 AA 分摊

支持：

- 均分余分，确保整数分合计守恒。
- 自定义每人份额。
- 本人已垫付、本次本人垫付、他人已垫付。
- 本人应付款的独立确认。
- 部分收款、重复查询、逾期、关闭剩余请求。
- 截止日期延期、历史日期保留。
- 确认时保存参与人身份快照。

例如 ¥398.01 四人均分可得到 ¥99.51、¥99.50、¥99.50、¥99.50，合计严格相等。

### 7.4 AA 汇总、筛选与导出

页面分别展示待收、本人应付、逾期和关闭未结清金额，并按状态筛选。

单笔对账单可本地导出。待收不是现金，关闭也不表示欠款被豁免或对方已经付款。

### 7.5 一次性与工资事件储蓄

已有已验证路径包括指定未来日期一次性转入，以及实际工资事件触发的月度储蓄。

工资未验证到账时跳过、不盲扣、不追补；一次性安排不会创建时立即扣款，到期仍检查资金、授权与保护底线。

支持暂停、恢复和取消，旧预览或条件变化后必须重新核对。

### 7.6 最新工作区：固定日月度转入

本轮新增每月指定日期 09:00 转入、月末夹取、跨月执行和取消后重新设置。固定日期模式不等待工资，错过日期或资金不足时停止，不透支或补扣。

**已通过消费者三尺寸回归和独立执行Worker验证。**

## 8. 理财操作

### 8.1 完整适配问卷

问卷综合用途、最早用钱日、损失容忍、流动性、经验、收入稳定性和风险理解情况。

零损失要求、应急用途或流动性约束可能使用户进入保留现金路径。界面不让用户直接选择一个高风险等级来绕过匹配规则。

### 8.2 产品与现金比较

在支持范围内给出最多三个适配产品，并保留现金选项；解释不匹配原因、费用、锁定期和固定模拟情景。

风险边界包含申购和赎回费用。净值不变、压力和乐观情景是确定性样例，不是经统计校准的收益概率或收益保证。

### 8.3 申购、份额与赎回

申购扣款、待确认和已确认份额分开；赎回检查锁定期和可用份额，冻结待赎回份额，到账前不能把它用来付款。

金额使用整数分，份额采用整数微份额与确定性运算，避免浮点金额误差。

### 8.4 截止时间与结算

使用固定模拟服务日历，包含 15:00 截止、周末和明确的模拟休市日，顺延受理后再按 T+1 结算。

此日历不代表现实市场或银行营业日历。演示日期与真实日期不同时，界面说明采用的演示时刻假设。

### 8.5 条款变化与异步回报

净值、费用和持有期变化会影响冻结的准备参数；停购、风险评估过期和旧审批失效时需重新准备。

模拟提供商回报包含签名、会话绑定、事件编号和版本。重复与乱序回报不会重复增加现金或份额，成功终态不会被旧 pending 覆盖。

## 9. 卡片生命周期

### 9.1 申请与审核

用户申请模拟借记卡或信用卡，查询待审、通过、拒绝和未知结果。页面展示申请额度、获批额度和部分批准原因。

缺少就业说明时，可补交合成在职或自由职业说明，再独立确认提交审核；不需要真实证件。审核中的申请可以按规则撤回。

### 9.2 激活与交易开关

新申请通过的卡初始锁定，用户单独确认解锁激活。线上和境外开关仍独立控制，不因申请通过而默认全部打开。

### 9.3 调额与资金边界

模拟调额可通过、部分批准或拒绝。拒绝时保留原额度；额度变化不增加活期现金、旅行金或目标覆盖金额。

### 9.4 锁定、挂失与补发

临时锁定可以独立解除；挂失不能普通解锁。补发新卡沿用结算账户，旧卡保持挂失，新卡初始锁定且支付开关关闭。

未知结果阻止重复补卡或冲突变更，先查询原操作。卡状态变化不自动取消已付订单。

### 9.5 支付影响查看

可查看关联旅行订单、预留、未知付款和退款状态，并按原单核对。

订阅卡绑定和逐商户换卡已完成本轮领域、三尺寸流程与未知结果恢复验证。

## 10. 旅行 Agent 请求、授权与跨场景支付

### 10.1 签名请求收件箱

旅行请求验证模拟 Agent 身份、HMAC、会话与目标主体、时间窗口及 nonce，检查币种、报价总价、税费、商户和有效期。

伪造、过期、重放和主体不匹配请求被拒绝。接受请求只表示允许进入订单核对，不等于创建付款权限。

### 10.2 可编辑授权

用户设置资金账户、目标、允许商户、单笔与累计上限及有效期。

修改前逐项比较旧值和新值，扩大金额、增加商户、延长期限都会提示。撤销只停止新订单，不能抹去已提交或未知订单，也不自动退款。

自然语言授权草稿采用有边界的确定性解析。缺少字段或包含不支持条件时，需要补充，不会默默忽略限制并创建授权。

### 10.3 预算协商与变更重确认

用户可按住宿总预算重新询价。当前由固定模拟商户规则生成新签名请求和替代关系。

例如原住宿总价 ¥2,200、可退，新报价 ¥2,150、不可退。NOVA 同时展示价格和退改变化，用户必须重新接受，再独立确认订单。

无法满足预算时明确失败；已付或未知订单不能用新报价覆盖。

### 10.4 付款前检查

系统重新核对：

- 当前有效报价和请求接受状态。
- 目标与来源账户。
- 可用资金、其他目标分配和预留。
- 卡状态、线上／境外开关及单笔限制。
- Mandate 商户范围、金额与期限。
- 原审批参数、状态版本和时效。

### 10.5 独立订单、未知与退款

机票和住宿各自保存订单与支付状态。一单成功、一单失败时，不能把成功单重新付款。

未知结果保留预留，查询原操作；取消和退款按条款独立处理。退款在途属于已扣未退的一部分，不能与其重复相加，更不能提前当成可用现金。

### 10.6 订单对账

提供预留、已扣未退、退款在途、已退和未知数量汇总、状态筛选及单笔本地 JSON 导出。

订单已确认不等于服务已履约，导出的对账单也不是现实商户履约证明。

## 11. 日期现金流与 What-if Lab

日期现金流把已知工资、固定账单、订阅、一次性支出和转入安排放在同一时间轴上。

用户可以查看最低余额及出现日期，或只读试算工资延迟、额外支出等变化。试算结果解释为什么某天可能付不起，而不仅是计算一个月末结余。

| 资金或状态 | 能否直接作为当前支付资金 |
| --- | --- |
| 已核对的可用账户余额 | 还需扣除保护额、其他目标和预留 |
| 预计未来工资 | 不能 |
| AA 待收 | 不能 |
| 待确认投资份额 | 不能 |
| 赎回在途 | 不能 |
| 退款在途 | 不能 |
| 信用卡额度 | 不计为现金；当前旅行付款不以信用额度替代借记资金 |
| 已预留资金 | 已被原操作占用，不能再给其他任务使用 |

预测是基于已提供数据和明确假设的判断，不保证工资、退款或交易在未来按预测发生。

## 12. 主动监测、提醒与失败恢复

### 12.1 监测对象

包括目标资金变化、工资事件、计划执行、订阅取消、续费风险、理财待结算、未知付款、卡片状态、订单失败与退款等。

已有统一问题收件箱把未解决事项关联到原操作，提供查询或人工处理路径。

### 12.2 最小必要行动

已有多目标调整限制在用户允许的加存、延期和保护范围内，不自动降低他人目标或扩大付款授权。

最新工作区增加旅行恢复候选：保持现状、查原单、只为失败服务重新询价、先核对退款等，并按声明的变化成本排序。它不自动取消成功单，也不对未知订单重付。

**新增恢复面板及仅失败项询价仍在本轮最终验收中。**

### 12.4 最新工作区：目标提醒偏好

新增每目标全部变化、仅需处理事项、静默偏好及本地已读队列，并遵守全局静默和暂停。

该提醒独立于付款授权；改变通知偏好不会授予或扩大金融操作权限。**已通过本轮领域及三尺寸专项验证。**

## 13. 核心创新点

NOVA 的创新主要体现在产品组织与工程机制的组合，而不是声称单项技术为行业首创。以下区分用户价值、实现方式和当前边界。

### 13.1 创新一：目标合同与金融授权分离

**问题**：用户说“我要准备旅行”，不代表 AI 可以任意扣款、买产品或提高限额。

**做法**：目标合同表达金额、期限、保护底线、优先级和可接受调整；Action / Mandate 独立表达具体执行权限。

**用户价值**：目标可以灵活修改，但钱仍在可理解的边界内。改目标不会偷偷扩大已有扣款授权。

**可展示例子**：将旅行金额提高后，旧旅行付款授权的累计上限保持原值，超出部分需要新确认。

**状态**：合同与授权分离已验证；目标提醒整合、本地队列与静默/暂停检查也已验证。

### 13.2 创新二：关注“哪一天能用”，而不只看“总共有多少”

**问题**：月结余为正，不代表账单扣款日或报价到期前有现金。

**做法**：用日期账本统一工资、续费、账单、转入、T+1 和未知占用，区分未来预计与当前可支付。

**用户价值**：避免用明天才到账的钱支付今天的订单，也能解释工资前的资金低谷。

**可展示例子**：赎回已提交，但款项未结算，NOVA 仍阻止使用这笔钱支付快到期的旅行报价。

**状态**：日期预测、一次性与工资事件转入、模拟结算已验证；固定日月度编辑、月末夹取及执行已补齐并验证。

### 13.3 创新三：付款后目标不会被误判为“退步”

**问题**：旅行钱包支付机票后余额减少，若只看存款进度，会误判目标倒退。

**做法**：分开计算目标现金、资金预留、有效订单和履约证据。

**用户价值**：能知道钱变成了什么，而不是只能看到账户余额下降。

**说明性示例**：在独立“旅行金已备齐”样例中，目标 ¥8,000，支付机票和住宿共 ¥5,000 后，剩余现金 ¥3,000，加有效订单 ¥5,000，仍能解释 ¥8,000 的资金去向；退款在途则单独暴露缺口。

**状态**：现金、预留、有效订单已验证；四进度和独立签名模拟履约已通过本轮领域、三尺寸和重启验证。

### 13.4 创新四：失败后只改变必要的部分

**问题**：一个步骤失败，普通自动化容易重跑整条流程，造成重复预订或重复付款。

**做法**：把成功、失败、未知和退款状态分别保存，在声明的候选空间内比较可行修复；成功项默认保留，未知项优先查询。

**用户价值**：不必因为酒店失败就重买机票，也不会把追查未知付款变成再付一次。

**边界**：“最小”指受限候选空间和明确的变化成本，不是对所有商户、产品与日期进行全局最优搜索。

**状态**：独立订单和有界多目标调整已有验证；新恢复面板和失败项专属询价已通过三尺寸检查，保留成功单且不重付未知单。

### 13.5 创新五：事实、假设、预测、授权与结果可追溯

**问题**：AI 给出一个数字，用户难以判断来自历史交易、未来假设还是已经发生的结果。

**做法**：将 Evidence、Forecast、Preview、Approval、Receipt 和 Audit 分开保存，解释引用相应来源。

**用户价值**：可以从“为什么付不起”“为什么建议取消”下钻到交易、资金占用、条款或原凭证，而不是接受一句解释。

**状态**：账单证据和执行审计已有验证；任务节点、执行凭证与批准引用的统一下钻已验证，来源保留自己的数据日期。

### 13.6 创新六：判断 Agent 是否仍在执行原意

**问题**：报价虽然更便宜，但商户、退改或付款方式已经变化，用户的原意可能被偏离。

**做法**：记录当前页面的旅行选择，对比商户、总价、税费、退改、有效期、账户和卡片；范围变化与新签名请求触发重新核对。

**用户价值**：不会只因降价就忽略“可退变不可退”，也不会在换了支付方式后继续沿用旧确认。

**可展示例子**：住宿 ¥2,200 可退改为 ¥2,150 不可退，价格更低仍须再次接受新条件。

**边界**：目前是确定性字段比较，原意记录仅在当前页面；不是通用语义理解或跨机构意图协议。

**状态**：已在对应模拟范围验证。

### 13.7 创新七：任务可以回放，而不是只留下聊天记录

**问题**：刷新、重启或演示被追问时，仅有对话文本无法证明哪一步执行、哪一步失败。

**做法**：保存原操作编号、任务版本、订单、批准和审计引用，提供脱敏证明包；新工作区加入持久检查点和 v1→v2 迁移。

**用户价值**：能够继续原任务、核对原操作，并解释执行过程，不必靠重新跑一遍来证明。

**边界**：证明包是相关工件和审计摘录，不是完整独立审计链或现实银行证明。

**状态**：原证明包与持久操作已有验证；新任务检查点、迁移、履约来源和重启恢复仍在本轮最终验收中。

### 13.8 支撑创新：将不确定性作为正式业务状态

“处理中”“已提交”不是成功的同义词。NOVA 将未知、待结算、退款在途、需商户处理等状态直接纳入用户流程。

用户因此能够理解哪些事实已确认、哪些钱还不能用、下一步应查什么。这个设计同时支撑可信解释和避免重复付款。

## 14. Agent 与确定性金融核心的分工

### 14.1 AI 的职责

AI 可参与目标理解、任务整理、只读调查、说明生成和候选解释。金融任务页也使用明确标识的确定性关键词适配，不把规则路由伪装成模型推理。

### 14.2 确定性代码的职责

金额计算、适配规则、份额、费用、状态迁移、可支付余额、权限、审批、预留、幂等、验证和审计由确定性代码处理。

模型不能自行宣称用户已确认，也不能通过一句解释修改账户余额。

### 14.3 13 类技能组织

| 技能 | 作用 |
| --- | --- |
| 账单导入与对账 | 检查批次、字段与重复／退款等问题 |
| 账单与订阅调查 | 汇总期间、比较基线、追踪周期扣费 |
| 日期现金流 | 解释工资、账单和可用资金时点 |
| 多目标规划 | 检查目标冲突和受限调整 |
| 转账与储蓄计划 | 读取安排和准备状态，进入受控确认流程 |
| 授权构建 | 理解并核对支持范围内的授权字段 |
| 外部请求收件箱 | 检查已验证的模拟旅行请求 |
| 结果监测与重规划 | 跟踪影响、执行结果和恢复候选 |
| 解释与来源 | 将结论绑定到可核对工件 |
| 人工交接 | 整理证据、未知项与已尝试动作 |
| 联系人与 AA 协调 | 读取对象身份、份额和结算状态 |
| 理财生命周期 | 读取适配、申赎和结算状态 |
| 卡片生命周期 | 读取卡状态、支付条件和操作结果 |

技能注册数量不代表模型已经熟练使用所有能力。部分适配为只读，具体执行必须由独立确定性流程和用户确认完成；真实六场景模型多轮评测仍待完成。

## 15. 安全与治理机制

NOVA 的金融写操作遵循：

**Permission → Risk → Execute → Verify → Audit**

| 机制 | 具体作用 |
| --- | --- |
| 严格共享契约 | 前后端使用一致的 Schema、整数分与 ISO 日期 |
| 准备／确认分离 | 展示精确对象、金额、条款和时效，再由用户确认 |
| 版本与快照 | 数据、报价、卡片或条款变化后，旧准备可能失效 |
| 权限边界 | 目标、请求接受、Mandate 与实际付款权相互分离 |
| 保护与预留 | 应急金、其他目标占用、未知付款不可被重复挪用 |
| 幂等与原操作查询 | 相同操作不重复执行，未知优先对账 |
| 签名、时间与 nonce | 对模拟 Agent 请求和服务回报进行身份与重放校验 |
| 事件版本与终态保护 | 旧回报不能把 settled 改回 pending |
| 会话隔离 | 不同会话的动作、证据和任务不能交叉访问 |
| Hash 审计 | 关键动作与结果形成可核验的链式记录 |
| Passkey 基础 | 仓库具备 Passkey 注册／认证及相应操作授权路径，具体入口按流程启用 |
| MCP 工具边界 | 通过受约束工具契约访问能力，不让模型直接操作数据库 |
| 服务端密钥 | DeepSeek 和签名密钥不进入前端、样例或普通日志 |
| 日志最小化 | 路由模板、自生关联 ID 和受控诊断，避免原文泄露 |
| 本地脱敏导出 | 使用字段白名单，不导出签名、密钥或批准令牌 |

“有治理机制”不等于已经达到真实银行准入、监管认证或生产安全审计标准。

## 16. 离线与恢复

PWA 离线摘要用于查看有限的目标评估和连接信息，不提供离线执行金融写操作的能力。

在线恢复时重新读取当前状态；旧离线摘要不能直接成为付款依据。SQLite 持久化保存模拟业务状态、操作与审计，避免仅依赖浏览器组件内存。

新工作区进一步增加任务检查点、版本迁移和履约证据关联，本轮验证已通过。真实外部提供商的网络补偿、持久 Outbox、密钥轮换和长期生产迁移不应被本地恢复测试替代。

## 18. 一条完整演示故事

### 18.1 看懂钱

用户从首页看到消费摘要，进入账单查看分类，核实餐饮支出变化和 CloudBox Plus 续费。

### 18.2 制定旅行目标

在首页新建目标中设置日本旅行金额和日期，比较存钱节奏，并保留应急金底线。

### 18.3 做一件可核对的改善

用户确认不再需要某项订阅，核对取消条款，查看服务端结果。成功后未来扣费预测变化，失败或未知则显示恢复路径。

### 18.4 安排资金

根据计划创建工资事件储蓄或一次性转入，明确创建此刻不扣款；与同行进行 AA 时，待收仍不计为可花现金。

### 18.5 准备受控付款

在独立已备钱样例中检查卡片、报价和 Mandate。用户接受签名请求，再单独核对订单付款。

### 18.6 让变化显形

模拟商户提供更低价格但不可退的新住宿方案。NOVA 展示条件差异，旧请求和旧付款准备不能直接继续。

### 18.7 处理失败与完成过程

一单成功、另一单失败时保留成功结果，未知先查原单，退款在途不计现金。恢复面板、模拟履约证据与持久任务检查点已通过本轮验收；仍需明确它们只操作合成数据。

## 20. 项目价值的表达方式

### 20.1 面向普通用户

“告诉 NOVA 你想完成什么，它帮你看清钱够不够、什么时候能用，以及下一步该做什么。真正动钱前，你能核对清楚；出现问题，也知道怎么继续。”

NOVA 用一个目标贯穿六类金融任务，将 LLM 的理解与解释能力和确定性算法、受控执行、证据追溯及恢复机制组合起来。价值不只在回答质量，还在任务能否安全、可解释地推进。

NOVA 的核心资产是统一状态与业务边界：数据质量、日期可用资金、目标合同、独立授权、执行状态和证据都需要互相对齐。新增能力应服务完整任务，而不是只增加页面入口。
