# 方案 B：开发分解、截止日前交付和评审

用户已选择方案 B 的方向。本文将完整设计转成可审查任务；业务开发应按依赖执行，不能把文档中的“拟实现”提前写成“已完成”。截止日为 2026-11-02；11-01 为功能冻结目标。

## 1. 本次承诺的产品边界

R1 是六场景完整的受控模拟产品：数据、规则、持久化、权限、预览、执行、验证、回执和恢复均真实运行；银行、商户、净值、审核和事件为可复现模拟。

可以收敛：商户/产品/人物数量、支持的导入版式、任务模板数、页面动效、品牌皮肤、协议适配和导出形式。

不能收敛掉：任何整类场景、申购或赎回一端、卡片申请/额度/限制解锁/挂失、联系人/定时/AA、年度与异常分析、订阅提醒与取消、跨订单部分失败、准确授权和资金一致性。

R1 支付主路径使用绑定明确账户的模拟借记卡；信用卡先完整提供申请、调额和控制。若扩展信用消费/账单还款，必须增加负债、清算和还款预算模型，不用“增加现金余额”假装信用支付。

## 2. 不覆盖用户改动的起点

1. 重新读取当前 HEAD、dirty files 与最新文档；先核对用户新开发，不按上次缓存重复实现。
2. 对现有未提交工作建立明确文件清单与可审查检查点，不 reset、clean 或覆盖。
3. 收集旧版服务端、浏览器、构建与模型结果的实际报告；定位未复核失败，不把旧数量写成新版本结果。
4. 保存 L0 基准和关键契约测试；审查新增范围与既有 PRODUCT/AGENT_SPEC 冲突。
5. 核心页面和资金链都在分支通过 PR 审查，不直接推 main。

## 6. 每个工作包的交付方式

每个工作包提供：需求编号、契约变化、业务逻辑、准确 UI 状态、正常和失败案例、迁移影响、测试结果、演示入口、已知限制。审查前完成可运行和可核对的结果。

开发顺序：业务规则/不变量 → 契约 → Provider/领域服务 → 状态和持久化 → API → UI → Agent → 故障和回归。不要先把六个漂亮页面都做完，再临时补状态。

完成意味着用户能走到底；有工具但无入口、有按钮但无服务端结果、有成功但无恢复、只有脚本而无实际资金/状态变化，均不算完成。

## 9. 发布门槛

### 9.1 必过

- 六类 R1 子能力全部有可操作入口和正常结果；失败/未知/拒绝不失联。
- 75 组基础验收及必要参数化变体、旧回归、迁移与会话隔离通过。
- 越权、重复资金副作用、资金/份额不守恒、关键结论无来源为零。
- 三故事各五次独立演示；包含至少一次刷新和一次重启恢复。
- 类型、构建、服务端/属性/HTTP、三宽度、严重无障碍问题通过。
- 真实模型报告包含实际完成、失败、fallback、调用限制和未测项；不能把降级算模型成功。
- 日志/导出/仓库无 Key、完整账户标识和真实个人账单；生产调试默认关闭。

### 9.2 不得虚报

无真实银行/商户接入就写模拟；未实现 AP2/ACP 兼容不宣称；未做真人研究不能以自动化代替；未测性能不写“毫秒级”；没有概率校准不写“成功率 95%”。

### 9.3 发布失败处理

先修资金与状态类缺陷，再修无法完成的流程、版本/恢复和界面阻挡；最后处理动效与非关键内容。不能为了展示六场景隐藏失败、伪造成功或禁掉校验。

如果截止前无法达到六类完整标准，提交材料必须准确列出已验证范围和未完成项，由团队决定提交策略；本方案不预先授权把“设计覆盖”说成“实现覆盖”。

## 10. 文档同步与后续反馈

选定详细范围后更新 PRODUCT、USER_FLOW、AGENT_SPEC、DESIGN_SYSTEM、DEMO_SCRIPT、IMPLEMENTATION_PLAN 和状态记录，保留历史版本与来源，不删掉用户已有设计。

最值得反馈的五项：

1. 主目标是否继续日本旅行，长期分支采用培训金还是其他目标。
2. 理财、卡片是否要比旅行订单占更多演示时间。
3. 希望九分钟完整讲故事，还是六类入口更便于逐项展示。
4. 哪些截图页面布局必须原样保留，哪些新页面可扩展。
5. 实际可投入人数与每日有效时间，以便把目标日历变成真实分工。

收到反馈后通过需求编号变更，附影响分析：增加哪项、替代哪项、依赖什么、影响哪些测试/页面/排期；不能只改标题而保持旧计划不变。
