# 聊天可靠性归因

基于当前代码静态检查；下述风险未全部由独立真实对话验证，不将推断当成已复现故障。

## 已确认的结构问题

1. `server/chat-routing.ts` 把页面选择、目标意图、知识回答、记忆切换、转账字段抽取塞入同一次输出，追加了多条例外优先级。目标参数在路由中被禁止提取，又要求路由识别具体参数改变，用途耦合。
2. `server/workspace.ts` 的目标分支再次调用 `understandGoalMessage`。同一句话串行经历路由模型与参数解析模型；两者上下文截断分别为 10 与 12 条，后者依赖 task facts 而非统一状态。
3. `server/understanding.ts` 先生成规则 fallback，即使模型成功仍将规则结果作为基础；已有规则字段会阻止模型覆盖。这不是只用于故障的 fallback，错误的规则理解可能压过模型结果。逐字金额存在不等于金额角色正确。
4. 状态分散为 chat memory、goal draft、agent task。`server/index.ts` 中 memoryAction=new 重建导航记忆，但未将“新目标”操作传入 `createAgentTurn`；`mergedGoalDraft` 按线程读取旧草稿再合并。存在新目标沿用旧预算、日期等字段的结构风险，需独立复现验证。
5. 仅记录粗粒度 `DEEPSEEK_INVALID_OR_TIMEOUT`，JSON 不合法、schema 不匹配、超时及网络异常混为一类。仅延长超时不能证明根因修复，也会增加等待时长。
6. 模型既决定 navigate 又判断金融任务，页面结构变化会影响对同一业务需求的理解。业务意图应独立于页面索引，再由确定映射生成导航。

## 应采用的重构边界

- 一次语义理解生成类型化的业务命令：操作类型、任务标识、目标/收款对象、字段补丁、逐字证据、不确定项、任务切换；不直接生成资金操作。
- 由统一任务状态机负责新建/续接/切换/取消与字段版本；新建目标清空前一目标的专属字段，保留原任务以支持恢复。
- 金额与日期的数值转换、权限、事实查询、计算及执行确认由确定代码负责。模型理解字段角色；规则验证有效性和证据，不凭正则先占语义字段。
- 路由是任务状态的输出：明确需要表单才映射页面；缺少材料只追问缺失项。自由解释与账户事实回答分离，后者必须有读取工具结果支持。
- 完整记录阶段耗时、错误分类与状态版本，记录中不包含密钥。只有暂时网络故障做有界重试；协议错误不原样重试。

## 评测更正

旧 97% 不可作为问答准确率。失败用例可回归，但独立验收集须冻结，不能用其逐句调整提示词。独立样本中同时验证任务识别、字段角色、状态隔离、数据依据、合理追问、页面与实际结果、无误执行，并按完整会话计成功率。分别报告模型理解失败、协议失败、状态失败、工具失败与前端失败。一次对话任一关键步骤错误即整段失败，不能用大量简单导航题稀释严重错误。

优先验收：两个目标连续创建、目标中断后转账再恢复、只改日期保留金额、预算与已存同额、纠正上一轮错误、多个对象与代词、未知数据、否定与撤销、多任务。开发集、回归集与未参与调优的验收集分别保存；失败与重试均计入可靠性统计。重构完成前不再宣称达到 95% 产品准确率。
